# Okooo 数据流水线实施方案评审报告

**日期**: 2026-01-26  
**评审对象**: HTML文件遍历与Markdown归档/向量化方案  
**评审结论**: 方案总体可行，但Phase 1面临严重反爬挑战，需调整策略。

## 1. 方案概述
本方案旨在构建一套自动化流水线，从 Okooo 网站爬取历史比赛数据，转换为 Markdown 格式，并存入 Chroma 向量数据库，最终为 Sports Betting 框架提供数据支持。

## 2. 技术可行性评估

### 2.1 核心流程
- **爬取 (Phase 1)**: 使用 Playwright 进行页面抓取。
  - **现状**: 原始方案可行，但实测发现阿里云 WAF 强拦截（405 Block）。
  - **风险**: 高。需引入代理池或人工辅助 Cookie 注入。
- **解析与清洗 (Phase 2)**: 使用 BeautifulSoup 和 Regex 提取数据。
  - **评估**: 可行。现有 `okooo_crawler.py` 已包含部分解析逻辑，需针对详情页进行优化。
- **向量化 (Phase 3)**: Markdown -> ChromaDB。
  - **评估**: 可行。Markdown 结构化文本适合 RAG (Retrieval-Augmented Generation) 场景。

### 2.2 关键问题分析：HTML 乱码
- **现象**: 原始 HTML 文件在浏览器或编辑器中显示乱码。
- **根因**: 
  - 源站 HTML 声明 `<meta charset="GBK">`。
  - 爬虫使用 UTF-8 编码保存文件，但未修改 `<meta>` 标签。
  - 浏览器/编辑器读取文件时，根据 `<meta>` 标签误以为是 GBK 编码，导致解码错误。
- **解决方案**: 在保存 HTML 前，强制将 `<meta charset="GBK">` 替换为 `<meta charset="utf-8">`，并确保文件以 UTF-8 格式写入。此修复已在 `okooo_crawler.py` 中验证实施。

## 3. 风险与依赖识别

### 3.1 风险
1.  **WAF 反爬拦截 (Critical)**:
    - 阿里云 WAF 检测到无头浏览器或频繁请求，直接返回 405。
    - **缓解措施**: 降低并发频率（已实施），随机 User-Agent（已实施但无效），引入高匿名代理池（建议），使用指纹浏览器（建议）。
2.  **数据结构变更**:
    - 源站页面结构可能随时调整。
    - **缓解措施**: 在 Phase 2 增加结构校验逻辑，失败时报警。

### 3.2 依赖
- Python 环境及 Playwright。
- 稳定的网络连接（需翻墙或国内优化线路）。
- ChromaDB 服务（本地或远程）。

## 4. 方案优化建议
1.  **增强反爬能力**: 优先解决 Phase 1 的 WAF 问题。建议尝试使用 `stealth` 插件或切换到 `requests` + 高级指纹库（如 `curl_cffi`）。
2.  **数据分层存储**:
    - Raw HTML (存证/回溯)
    - Cleaned JSON (结构化数据，用于训练/分析)
    - Markdown (语义化数据，用于向量检索)
3.  **增量更新**: 增加去重逻辑，避免重复爬取。

## 5. 结论
方案架构合理，但第一步数据获取受阻。建议暂停后续阶段开发，集中资源攻克 Phase 1 的反爬问题，或寻找替代数据源。
