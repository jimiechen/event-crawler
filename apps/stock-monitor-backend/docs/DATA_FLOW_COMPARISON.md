# 数据流方案对比分析报告

**日期**: 2026-01-11
**对比对象**:
1.  **方案 A**: `2026-01-10/All_DATA_FLOW.md` (V1.0/全量梳理版)
2.  **方案 B**: `DATA_FLOW_2026.md` (V2.0/最新设计版)

---

## 1. 核心差异总结

两份文档的主要差异在于 **侧重点不同** 和 **实时处理架构的实现路径** 不同。

| 维度 | 方案 A (All_DATA_FLOW.md) | 方案 B (DATA_FLOW_2026.md) |
| :--- | :--- | :--- |
| **文档定位** | **全系统参考手册**：包含详细的数据库 Schema、现有所有服务类的说明、以及初步的改造构想。 | **实施落地指南**：专注于解决"如何集成 Pathway 引擎"这一具体问题，侧重于数据流向和交互时序。 |
| **实时数据入口** | 建议新增 `/api/v1/realtime/stock-data` 接口。 | **复用现有** `/api/v1/stocks/data/batch` 接口，降低插件端改造除成本。 |
| **处理引擎架构** | 提议新建 `RealtimeMonitorEngine` 独立服务。 | **集成模式**：在 `StockService` 中异步调用现有的 `PathwayEngine`，复用其计算逻辑。 |
| **告警机制** | 未详细展开，仅提到预警记录表 (`alert_record`)。 | **明确引入 SSE (Server-Sent Events)**，实现毫秒级主动推送前端。 |
| **数据库描述** | **非常详细**：列出了所有表结构、字段类型、索引和枚举值。 | **精简**：假设数据库结构已就绪，仅关注数据如何在组件间流动。 |

---

## 2. 方案 A 深度分析 (All_DATA_FLOW.md)

**优点**:
*   **资产盘点全面**: 详细列出了 `stock_daily`, `volume_analysis_result` 等核心表的结构，是项目验收和维护的重要字典。
*   **现状描述准确**: 对现有的 `StockDataManager`, `MonitorService` 等类的功能描述非常到位。

**不足**:
*   **架构冗余**: 提出的 `RealtimeMonitorEngine` 可能会与现有的 `PathwayEngine` 逻辑重复。
*   **实施复杂度高**: 新增 API 意味着 Chrome Extension 也需要大幅修改推送逻辑。
*   **缺少闭环**: 对"告警产生后如何触达用户"（前端展示）描述较少。

---

## 3. 方案 B 深度分析 (DATA_FLOW_2026.md)

**优点**:
*   **开发成本低**: 通过修改 `StockService.submit_stock_data` 插入异步任务，无需破坏现有 API 契约，插件端改动极小。
*   **逻辑复用**: 强调复用 `PathwayEngine` 的核心算法，避免了"盘中一套代码，盘后一套代码"的维护陷阱。
*   **交互体验好**: 引入 SSE 使得告警具备实时性，符合"实时监控"的业务目标。
*   **时序清晰**: Mermaid 图表清晰展示了毫秒级的数据流转。

**不足**:
*   **缺少底层细节**: 没有列出数据库表结构，开发时需配合方案 A 使用。

---

## 4. 结论与建议

**结论**:
方案 A 和 方案 B 并非对立关系，而是 **互补关系**。
*   **方案 A** 是项目的 **静态架构蓝图**（数据库、类结构）。
*   **方案 B** 是本阶段的 **动态实施方案**（数据流、时序）。

**最终建议 (Action Plan)**:

1.  **架构落地采用方案 B**:
    *   **保持 API 不变**: 继续使用 `/api/v1/stocks/data/batch`。
    *   **服务层集成**: 在 `StockService` 中注入 `PathwayEngine`。
    *   **前端通信**: 落地 SSE 服务。

2.  **数据字典沿用方案 A**:
    *   开发过程中涉及数据库变更或查询时，以方案 A 中的表结构定义为准。
    *   `stock_score_result` 和 `volume_analysis_result` 表结构设计非常合理，直接沿用。

3.  **文档合并**:
    *   建议以方案 B 为主干，将方案 A 中的"二、核心数据库表结构"章节作为附录追加到方案 B 中，形成一份最终的 **V2.1 项目技术白皮书**。
